### 2.1 What the guards actually are — §2.4 classification

`core/action-authority.js:7-16` (`assertModuleAction`) and `:23-29` (`executeOwnedAction`):

```js
export async function executeOwnedAction(moduleName, action, runner, meta={}){
  ensureCurrentUserActive(`${moduleName}:${action}`);
  assertModuleAction(moduleName, action);
  auditAction(moduleName, action, {…stage:'started'…});
  try { const result=await runner(); auditAction(…'completed'…); return result; }
  catch(error){ auditAction(…'failed'…); toast?.(…); throw error; }
}
```

`assertModuleAction` **throws** on three conditions: unknown module boundary; action owned by another module and caller not in `allowedInvokers`; action not registered for the module.

| Control | §2.4 classification |
|---|---|
| Route access (`canCurrentUserAccess` in `router.js:2`) | **route guard** — runs before mount, renders a terminal denial |
| `executeOwnedAction` / `assertModuleAction` | **client-side check** — throws in the browser, genuinely blocks the call path |
| `ensureCurrentUserActive` | **client-side check** — denies on `status !== 'active'` |
| `confirmAction` | **visual-only** — a confirmation dialog, not an authorization control |
| Proxy authorization | deferred to Phase 2 |

All of these execute in the browser. Whether any survives a caller who does not use the browser is the Phase 2 question.

### 4.3 The pattern the brief asked to test

> *"are the portals deployed products, or abandoned trees kept alive only by test references?"*

**They are three different things, and conflating them would be wrong:**

- **`ECM_ActivityHub_Portal/` is a maintained product.** It is a first-class entry point in the import checker, is loaded by the smoke suite, has its own auth posture assertions, gets config generated for it, and has a dedicated npm script. 53 files, actively wired.
- **`document-portal/` is a deployed-shaped product with no maintenance harness.** 41 files, its own service worker, manifest, robots.txt and sitemap — the artefacts of something intended to be hosted. But nothing loads it, nothing tests its behaviour, and the one test that touches it reads its source as text.
- **`newack/` is abandoned.** Its sole tie to the repository is that it holds a credential the scanner suppresses. Remove `tests/secrets-baseline.txt:2` and nothing in the repository would reference it at all.

**`newack/` is the sharpest result of Phase 1**: an orphaned tree whose only reason to still be indexed is a live-shaped credential (`F-001`). It has 791 lines, three HTML pages, and no owner.

### 4.4 Notable architectural property — server imports client config

`proxy/src/authorize.js:10` importing `config/rbac.config.js` means **the permission matrix has exactly one definition**, shared by the browser and the server. This is a genuinely good property: it removes the usual drift between a client's idea of a role and a server's. It also creates a coupling — the server cannot be deployed without the client's `config/` tree on disk, and `proxy/` has no `package.json`, so it inherits `"type": "module"` from the repository root.

Whether the proxy's *use* of that shared matrix is faithful is the Phase 2 question and is not asserted here.
